\chapter*{Installing R and RStudio}\label{installing-r-and-rstudio}
\addcontentsline{toc}{chapter}{Installing R and RStudio}

\markboth{Installing R and RStudio}{Installing R and RStudio}

Two separate pieces of software are needed, and the distinction between
them causes more confusion than it should. \textbf{R} is the language:
the engine that does the computing. \textbf{RStudio} is the environment
you work in: the editor, the panes, the buttons. RStudio cannot do
anything without R behind it, which is why R goes first.

Everything here is free, and the whole process takes about fifteen
minutes on a normal connection. Do it before the first session on 2
September rather than during it.

\section*{Step 1: install R}\label{step-1-install-r}
\addcontentsline{toc}{section}{Step 1: install R}

\markright{Step 1: install R}

Go to \href{https://cran.r-project.org}{\textbf{cran.r-project.org}} and
choose the download link for your system.

\textbf{On Windows}, click \emph{Download R for Windows}, then
\emph{base}, then the download link at the top. Run the installer and
accept the defaults.

\textbf{On macOS}, click \emph{Download R for macOS} and pick the
correct \texttt{.pkg} file. There are usually two. If your Mac has an
Apple silicon chip (M1, M2, M3, or M4), take the \textbf{arm64} version.
If it has an Intel chip, take the other. To check, click the Apple menu,
then \emph{About This Mac}, and read the Chip or Processor line.

Choosing the wrong one on a Mac is the single most common installation
problem, and it produces confusing errors later rather than a clear
failure at install time.

\section*{Step 2: install RStudio}\label{step-2-install-rstudio}
\addcontentsline{toc}{section}{Step 2: install RStudio}

\markright{Step 2: install RStudio}

Go to
\href{https://posit.co/download/rstudio-desktop}{\textbf{posit.co/download/rstudio-desktop}}.
The page detects your system and offers the right installer. Take the
free Desktop version; there is no need for any paid tier or for RStudio
Server.

Install it, then open \textbf{RStudio}, not R. From here on, RStudio is
the only one of the two you will launch directly.

\section*{Step 3: check that it
worked}\label{step-3-check-that-it-worked}
\addcontentsline{toc}{section}{Step 3: check that it worked}

\markright{Step 3: check that it worked}

You should see four panes, or two panes with tabs. Find the
\textbf{Console}, on the left, and type this at the
\texttt{\textgreater{}} prompt, then press Enter.

\begin{Shaded}
\begin{Highlighting}[]
\DecValTok{2} \SpecialCharTok{+} \DecValTok{2}
\end{Highlighting}
\end{Shaded}

If \texttt{{[}1{]}\ 4} appears, both pieces are installed and talking to
each other.

Then check the version:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{R.version.string}
\end{Highlighting}
\end{Shaded}

Anything from \textbf{R 4.3.0} onward is fine for this course. If you
have an older installation lying around from a previous course, update
it now rather than debugging a version problem in Week 3.

\section*{Step 4: install the
packages}\label{step-4-install-the-packages}
\addcontentsline{toc}{section}{Step 4: install the packages}

\markright{Step 4: install the packages}

A package is a bundle of functions someone else has written and shared.
R ships with a great many built in, and everything else is installed
once and then loaded whenever needed.

Run this in the Console. It will take several minutes and produce a
large amount of scrolling output, which is normal.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{install.packages}\NormalTok{(}\FunctionTok{c}\NormalTok{(}\StringTok{"tidyverse"}\NormalTok{, }\StringTok{"rmarkdown"}\NormalTok{, }\StringTok{"knitr"}\NormalTok{))}
\end{Highlighting}
\end{Shaded}

Then confirm they load:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{library}\NormalTok{(tidyverse)}
\end{Highlighting}
\end{Shaded}

You will see a short message listing the packages that came along with
it and noting a couple of conflicts. That message is informational, not
an error.

The remaining packages, for classification, text, and language model
work, are installed in the week they are first needed. There is no
advantage to installing everything now.

\section*{Step 5: install Quarto}\label{step-5-install-quarto}
\addcontentsline{toc}{section}{Step 5: install Quarto}

\markright{Step 5: install Quarto}

Quarto renders documents that combine code, prose, and output, and your
final project is submitted in that form.

Recent versions of RStudio include it already. Check in the Console:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{quarto}\SpecialCharTok{::}\FunctionTok{quarto\_version}\NormalTok{()}
\end{Highlighting}
\end{Shaded}

If that returns a version number, you are done. If it reports that the
package is not installed, run \texttt{install.packages("quarto")} and
try again. If it still cannot find Quarto itself, download it from
\href{https://quarto.org/docs/get-started}{\textbf{quarto.org/docs/get-started}}
and install it separately.

\section*{When installation goes
wrong}\label{when-installation-goes-wrong}
\addcontentsline{toc}{section}{When installation goes wrong}

\markright{When installation goes wrong}

Three problems account for nearly all of them.

\textbf{``Package not available'' or a compilation error on macOS.}
Almost always the arm64 and Intel mismatch from Step 1. Uninstall R,
check your chip, and install the matching version.

\textbf{Permission denied, or the installation appears to succeed but
the package will not load.} Common on university-managed laptops, where
the default library folder is not writable. R usually offers to use a
personal library instead, and you should accept. If it does not offer,
run this once and then reinstall:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{dir.create}\NormalTok{(}\FunctionTok{Sys.getenv}\NormalTok{(}\StringTok{"R\_LIBS\_USER"}\NormalTok{), }\AttributeTok{recursive =} \ConstantTok{TRUE}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

\textbf{The download stalls or times out.} More often a network problem
than a problem with your machine. Try again, and if it persists, try a
different connection or a different CRAN mirror, which you can choose
under \textbf{Tools \textgreater{} Global Options \textgreater{}
Packages}.

If none of these apply, bring the laptop to the first session. A
five-minute look in person is faster than an evening of email, and
installation problems are common enough that nobody should feel behind
because of one.

\section*{A little configuration}\label{a-little-configuration}
\addcontentsline{toc}{section}{A little configuration}

\markright{A little configuration}

Two settings are worth changing now. Go to \textbf{Tools \textgreater{}
Global Options \textgreater{} General} and:

\begin{itemize}
\tightlist
\item
  Set \textbf{Save workspace to .RData on exit} to \textbf{Never}.
\item
  Untick \textbf{Restore .RData into workspace at startup}.
\end{itemize}

Chapter 3 explains why these matter. In short, they are what make it

appearing to.

While you are in Global Options, \textbf{Appearance} lets you change the
theme and font size. Not important, but you will be looking at this
window for eight weeks, so it is worth a minute.

\chapter*{Four Ways to Run R Code}\label{four-ways-to-run-r-code}
\addcontentsline{toc}{chapter}{Four Ways to Run R Code}

\markboth{Four Ways to Run R Code}{Four Ways to Run R Code}

Within the first hour of using RStudio you will encounter at least four
different places where R code can be typed and executed: the console, a
script, an R Markdown document, and a Quarto document. Students almost
always assume that one of these is the real way to work and that the
others are variations on it, and they then spend the semester wondering
which one they were supposed to be using. The assumption is
understandable, and it is wrong. The four are not competing versions of
the same thing. Each answers a different question, and the question you
are asking should determine which one you open.

The distinction matters more in this course than it would in an
introductory statistics class. Your final project is submitted as a
document that must run from raw inputs to reported numbers on a machine
that is not yours. Ten percent of its grade depends on that property
alone. Understanding what each of these environments preserves, and what
each of them quietly discards, is therefore not a preliminary detail. It
is the foundation of everything you submit.

\section*{The console: thinking out
loud}\label{the-console-thinking-out-loud}
\addcontentsline{toc}{section}{The console: thinking out loud}

\markright{The console: thinking out loud}

The console is the panel where R is actually running. When you type
\texttt{2\ +\ 2} and press Enter, the console evaluates the expression,
prints the answer, and forgets that you asked.

\begin{Shaded}
\begin{Highlighting}[]
\DecValTok{2} \SpecialCharTok{+} \DecValTok{2}
\CommentTok{\#\textgreater{} [1] 4}
\end{Highlighting}
\end{Shaded}

That last property is the important one. The console keeps a history you
can scroll through, but it keeps no record you can hand to anyone, and
it imposes no order on what you did. If you fit a model, adjust a
variable, fit it again, and then produce a result you are pleased with,
the console cannot tell you which sequence of steps produced it. Neither
can you, a week later.

The console is therefore the right tool for questions you are asking of
yourself rather than of the world. Checking the dimensions of a dataset,
inspecting a variable, reading a help file, and testing whether a line
does what you expect are all console work. Use it constantly, and use it
freely. Nothing you do there is precious, which is precisely what makes
it useful.

\section*{The script: a record of
instructions}\label{the-script-a-record-of-instructions}
\addcontentsline{toc}{section}{The script: a record of instructions}

\markright{The script: a record of instructions}

An R script, saved with the extension \texttt{.R}, is a plain text file
containing lines of R code and nothing else. When you run a script, R
executes each line in order, exactly as if you had typed them into the
console yourself.

The difference is that the file survives. A script is a record of what
you did, in the order you did it, and it can be run again tomorrow, or
by someone else, or by you on a different machine. This is what makes it
the first genuinely reproducible unit of work, and it is why the
transition from console to script is the single most consequential habit
shift in learning R.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# analysis.R}
\FunctionTok{library}\NormalTok{(tidyverse)}

\NormalTok{fl }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"https://raw.githubusercontent.com/babakrezaee/AppliedAI{-}PoliSci/main/data/FearonLaitin2003.csv"}\NormalTok{)}

\NormalTok{fl\_clean }\OtherTok{\textless{}{-}}\NormalTok{ fl }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{filter}\NormalTok{(}\SpecialCharTok{!}\FunctionTok{is.na}\NormalTok{(onset)) }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{mutate}\NormalTok{(}\AttributeTok{log\_pop =} \FunctionTok{log}\NormalTok{(pop))}

\NormalTok{model }\OtherTok{\textless{}{-}} \FunctionTok{glm}\NormalTok{(onset }\SpecialCharTok{\textasciitilde{}}\NormalTok{ log\_pop }\SpecialCharTok{+}\NormalTok{ gdpen, }\AttributeTok{data =}\NormalTok{ fl\_clean, }\AttributeTok{family =} \StringTok{"binomial"}\NormalTok{)}
\FunctionTok{summary}\NormalTok{(model)}
\end{Highlighting}
\end{Shaded}

As explained in the previous section, you can check the dimension of
your datasets and summarize your variables as well:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{dim}\NormalTok{(fl)}
\FunctionTok{summary}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{gdpen)}
\NormalTok{?mean}
\end{Highlighting}
\end{Shaded}

What a script preserves is the instructions. What it does not preserve
is the output. Run the script and the results appear in the console,
where they are as ephemeral as anything else typed there. Run it again
in three months, after the data file has been updated or a package has
changed, and you may get different numbers with no record of what the
old ones were. Scripts are also, by design, hostile to prose. You can
write comments, and you should, but a comment is a note to yourself, not
an argument addressed to a reader.

Scripts remain the right choice for work whose product is an action
rather than a document: downloading and cleaning a dataset, defining
functions you will use elsewhere, or running a long job whose output is
a saved file. In the repository for this course you will find several
such scripts in the \texttt{R/} folder.

\section*{R Markdown: code, prose, and output in one
file}\label{r-markdown-code-prose-and-output-in-one-file}
\addcontentsline{toc}{section}{R Markdown: code, prose, and output in
one file}

\markright{R Markdown: code, prose, and output in one file}

An R Markdown document, saved as \texttt{.Rmd}, holds three things at
once: prose written in Markdown, chunks of R code, and the output those
chunks produce. When you knit the document, R runs every chunk in order,
captures the results, and weaves them into a finished report as HTML,
PDF, or Word.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{{-}{-}{-}}
\AnnotationTok{title:}\CommentTok{ "Civil War Onset"}
\AnnotationTok{output:}\CommentTok{ html\_document}
\CommentTok{{-}{-}{-}}

\NormalTok{Fearon and Laitin (2003) report that per capita income predicts}
\NormalTok{civil war onset more reliably than measures of ethnic diversity.}
\NormalTok{The model below reproduces that pattern.}

\InformationTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}\{r\}}
\NormalTok{model }\OtherTok{\textless{}{-}} \FunctionTok{glm}\NormalTok{(onset }\SpecialCharTok{\textasciitilde{}}\NormalTok{ gdpen }\SpecialCharTok{+}\NormalTok{ ethfrac, }\AttributeTok{data =}\NormalTok{ fl, }\AttributeTok{family =} \StringTok{"binomial"}\NormalTok{)}
\FunctionTok{summary}\NormalTok{(model)}
\InformationTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}}

\NormalTok{The coefficient on income is negative and precisely estimated,}
\NormalTok{while the coefficient on ethnic fractionalization is not}
\NormalTok{distinguishable from zero.}
\end{Highlighting}
\end{Shaded}

Two consequences follow, and both matter for this course.

The first is that the numbers in your text cannot drift away from the
numbers your code produced, because the document generates them each
time it is knitted. A reported coefficient that was copied by hand into
a sentence will eventually become wrong, quietly, when the analysis
changes and the sentence does not. A reported coefficient that is
produced by the code cannot.

The second is subtler and catches almost everyone at least once.
Knitting starts a fresh R session that knows nothing about your
workspace. Any object you created in the console, any package you loaded
by hand, and any file path that happens to work on your machine are all
invisible to it. A document that runs perfectly line by line in your own
session will therefore fail to knit if it depends on something you did
outside it. This is not an inconvenience to be worked around. It is the
mechanism that makes the format trustworthy, because a document that
knits from a clean session is a document that will run on someone else's
computer.

The habit that follows is simple and worth adopting now: before you
submit anything, restart R (Session, then Restart R) and knit. If it
does not run from clean, it does not run.

\section*{Quarto: the same idea, more
broadly}\label{quarto-the-same-idea-more-broadly}
\addcontentsline{toc}{section}{Quarto: the same idea, more broadly}

\markright{Quarto: the same idea, more broadly}

Quarto, saved as \texttt{.qmd}, is the successor to R Markdown.
Everything described above applies to it unchanged, and if you have
understood R Markdown you already understand Quarto.

The differences are largely a matter of reach. Quarto is not tied to R,
so the same document can execute chunks written in Python or Julia,
which is directly relevant given that most of the applied AI ecosystem
lives in Python. Its options are declared in a consistent way across
output formats, and it renders books and websites as readily as single
documents. The materials you are reading now are a Quarto book.

\begin{Shaded}
\begin{Highlighting}[]
\InformationTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}\{r\}}
\CommentTok{\#| label: fig{-}onset}
\CommentTok{\#| fig{-}cap: "Predicted probability of onset by income"}
\CommentTok{\#| warning: false}

\FunctionTok{ggplot}\NormalTok{(fl, }\FunctionTok{aes}\NormalTok{(}\AttributeTok{x =}\NormalTok{ gdpen, }\AttributeTok{y =}\NormalTok{ fitted)) }\SpecialCharTok{+}
  \FunctionTok{geom\_line}\NormalTok{()}
\InformationTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}}
\end{Highlighting}
\end{Shaded}

For a single analysis document the practical difference between the two
is small, and either is acceptable for your final project. I use Quarto
for course materials because it handles a multi-chapter book cleanly,
and I would suggest it for new work on the general principle that
development effort is going there rather than into R Markdown.

The rule of thumb is short. Explore in the console, because it costs

\section*{Exercise}\label{exercise}
\addcontentsline{toc}{section}{Exercise}

\markright{Exercise}

Work through this in order. It takes about fifteen minutes and it is
worth doing before the first session rather than during it.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  In the console, compute \texttt{mean(c(4,\ 8,\ 15,\ 16,\ 23,\ 42))}.
  Note that the answer appears and then nothing remains except a history
  entry.
\item
  Open a new script (File, New File, R Script). Write the same line,
  save the file as \texttt{first-script.R}, and run it with the Source
  button. The result appears in the console again, but the instruction
  now lives in a file you could send to someone.
\item
  Open a new Quarto document (File, New File, Quarto Document). Write
  one sentence of prose describing what you are about to compute, then a
  code chunk containing the same line, then one sentence interpreting
  the result. Render it.
\item
  Now break it deliberately. In the console, create an object with
  \texttt{x\ \textless{}-\ c(4,\ 8,\ 15,\ 16,\ 23,\ 42)}. Change the
  chunk in your Quarto document to \texttt{mean(x)} and render again.
\end{enumerate}

The render fails, and the error will say that \texttt{x} was not found.
Sit with that for a moment before fixing it, because you have just met
the most common reason a working analysis refuses to knit the night
before a deadline. The object exists in your session and does not exist
in the document. The fix is to define \texttt{x} inside the document,
which is also the reason the format can be trusted.

\chapter*{Objects, Vectors, and Data
Frames}\label{objects-vectors-and-data-frames}
\addcontentsline{toc}{chapter}{Objects, Vectors, and Data Frames}

\markboth{Objects, Vectors, and Data Frames}{Objects, Vectors, and Data
Frames}

Everything in R is an object, and almost everything you will do in this
course amounts to creating an object, inspecting it, and passing it to a
function. This chapter covers the three kinds of object you will meet
constantly: the vector, which holds a column of values; the data frame,
which holds a table of them; and the individual value, which is really
just a vector of length one.

The order matters. Data frames are what political science data actually
look like, and they are the destination. Vectors come first because a
data frame is built out of them, and because most of the errors you will
hit in Week 2 come from a vector quietly being the wrong type.

\section*{Assignment}\label{assignment}
\addcontentsline{toc}{section}{Assignment}

\markright{Assignment}

An object is created by assigning something a name. R accepts two
operators for this, and you will see both in the wild.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{x }\OtherTok{\textless{}{-}} \DecValTok{5}
\NormalTok{y }\OtherTok{=} \DecValTok{5}
\end{Highlighting}
\end{Shaded}

Use \texttt{\textless{}-}. The two are equivalent in this context, but
\texttt{=} also means other things in R, including naming an argument
inside a function call, so keeping the two visually distinct saves
confusion later. In RStudio, \textbf{Alt and minus} on Windows or
\textbf{Option and minus} on a Mac types it for you.

To see what an object contains, type its name.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{x}
\CommentTok{\#\textgreater{} [1] 5}
\end{Highlighting}
\end{Shaded}

To remove one, use \texttt{rm()}.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{rm}\NormalTok{(x)}
\end{Highlighting}
\end{Shaded}

Names are subject to a few rules. They may contain letters, numbers, a
period, and an underscore, but not spaces or symbols such as \texttt{!},
\texttt{+}, or \texttt{\#}. They cannot begin with a number. And R is
case sensitive, so \texttt{polity} and \texttt{Polity} are two different
objects, which is a more common source of ``object not found'' than
anyone expects.

\section*{Vectors}\label{vectors}
\addcontentsline{toc}{section}{Vectors}

\markright{Vectors}

A vector is an ordered collection of values of the same type. You build
one with \texttt{c()}, for combine.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{gdp }\OtherTok{\textless{}{-}} \FunctionTok{c}\NormalTok{(}\FloatTok{2.1}\NormalTok{, }\FloatTok{4.7}\NormalTok{, }\FloatTok{1.3}\NormalTok{, }\FloatTok{8.9}\NormalTok{)}
\NormalTok{gdp}
\CommentTok{\#\textgreater{} [1] 2.1 4.7 1.3 8.9}
\end{Highlighting}
\end{Shaded}

Sequences of consecutive integers have a shorthand.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{years }\OtherTok{\textless{}{-}} \DecValTok{1990}\SpecialCharTok{:}\DecValTok{1995}
\NormalTok{years}
\CommentTok{\#\textgreater{} [1] 1990 1991 1992 1993 1994 1995}
\end{Highlighting}
\end{Shaded}

The phrase ``of the same type'' is the part worth pausing on, and it is
where the first real surprise lives.

\section*{Types, and why they matter}\label{types-and-why-they-matter}
\addcontentsline{toc}{section}{Types, and why they matter}

\markright{Types, and why they matter}

A vector holds numbers, or text, or logical values, but never a mixture.
If you supply a mixture, R does not complain. It silently converts
everything to the most accommodating type, which is almost always text.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{v1 }\OtherTok{\textless{}{-}} \FunctionTok{c}\NormalTok{(}\DecValTok{1}\NormalTok{, }\DecValTok{2}\NormalTok{, }\DecValTok{3}\NormalTok{)}
\NormalTok{v2 }\OtherTok{\textless{}{-}} \FunctionTok{c}\NormalTok{(}\DecValTok{1}\NormalTok{, }\DecValTok{2}\NormalTok{, }\StringTok{"a"}\NormalTok{)}

\NormalTok{v1}
\CommentTok{\#\textgreater{} [1] 1 2 3}

\NormalTok{v2}
\CommentTok{\#\textgreater{} [1] "1" "2" "a"}
\end{Highlighting}
\end{Shaded}

Look closely at \texttt{v2}. The numbers now have quotation marks around
them. They are no longer numbers, and arithmetic on them will fail.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{mean}\NormalTok{(v2)}
\CommentTok{\#\textgreater{} Warning: argument is not numeric or logical: returning NA}
\end{Highlighting}
\end{Shaded}

This behavior, called coercion, is the single most common reason a
calculation returns \texttt{NA} for no visible reason. A real dataset
with one stray text entry in an otherwise numeric column, for instance a
\texttt{"n/a"} typed by hand, will import as a text column and every
subsequent calculation on it will quietly fail.

The habit that protects you is to check the type whenever a result
surprises you.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{class}\NormalTok{(v1)}
\CommentTok{\#\textgreater{} [1] "numeric"}

\FunctionTok{class}\NormalTok{(v2)}
\CommentTok{\#\textgreater{} [1] "character"}
\end{Highlighting}
\end{Shaded}

Logical vectors hold \texttt{TRUE} and \texttt{FALSE}, and you will meet
them constantly as the result of a comparison.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{gdp }\SpecialCharTok{\textgreater{}} \DecValTok{3}
\CommentTok{\#\textgreater{} [1] FALSE  TRUE FALSE  TRUE}
\end{Highlighting}
\end{Shaded}

\section*{Arithmetic happens element by
element}\label{arithmetic-happens-element-by-element}
\addcontentsline{toc}{section}{Arithmetic happens element by element}

\markright{Arithmetic happens element by element}

Operations on vectors apply to every element at once, which is why R
rarely needs the loops that other languages depend on.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{a }\OtherTok{\textless{}{-}} \FunctionTok{c}\NormalTok{(}\DecValTok{1}\NormalTok{, }\DecValTok{3}\NormalTok{, }\DecValTok{5}\NormalTok{, }\DecValTok{7}\NormalTok{)}
\NormalTok{b }\OtherTok{\textless{}{-}} \FunctionTok{c}\NormalTok{(}\DecValTok{1}\NormalTok{, }\DecValTok{2}\NormalTok{, }\DecValTok{4}\NormalTok{, }\DecValTok{8}\NormalTok{)}

\NormalTok{a }\SpecialCharTok{*} \DecValTok{5}
\CommentTok{\#\textgreater{} [1]  5 15 25 35}

\NormalTok{a }\SpecialCharTok{+}\NormalTok{ b}
\CommentTok{\#\textgreater{} [1]  2  5  9 15}
\end{Highlighting}
\end{Shaded}

If the two vectors are of unequal length, R recycles the shorter one to
match the longer, rather than raising an error.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{c}\NormalTok{(}\DecValTok{10}\NormalTok{, }\DecValTok{20}\NormalTok{) }\SpecialCharTok{+} \FunctionTok{c}\NormalTok{(}\DecValTok{1}\NormalTok{, }\DecValTok{2}\NormalTok{, }\DecValTok{3}\NormalTok{, }\DecValTok{4}\NormalTok{)}
\CommentTok{\#\textgreater{} [1] 11 22 13 24}
\end{Highlighting}
\end{Shaded}

This is occasionally convenient and frequently dangerous. If you did not
intend the recycling, you now have a result that looks plausible and is
wrong. When two vectors should be the same length, check with
\texttt{length()} before combining them.

\section*{Getting at parts of a
vector}\label{getting-at-parts-of-a-vector}
\addcontentsline{toc}{section}{Getting at parts of a vector}

\markright{Getting at parts of a vector}

Square brackets extract elements by position, counting from one rather
than from zero.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{gdp[}\DecValTok{2}\NormalTok{]}
\CommentTok{\#\textgreater{} [1] 4.7}

\NormalTok{gdp[}\FunctionTok{c}\NormalTok{(}\DecValTok{1}\NormalTok{, }\DecValTok{3}\NormalTok{)]}
\CommentTok{\#\textgreater{} [1] 2.1 1.3}

\NormalTok{gdp[}\SpecialCharTok{{-}}\DecValTok{1}\NormalTok{]        }\CommentTok{\# everything except the first}
\CommentTok{\#\textgreater{} [1] 4.7 1.3 8.9}
\end{Highlighting}
\end{Shaded}

You can also select with a logical condition, which is the form you will
use most.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{gdp[gdp }\SpecialCharTok{\textgreater{}} \DecValTok{3}\NormalTok{]}
\CommentTok{\#\textgreater{} [1] 4.7 8.9}
\end{Highlighting}
\end{Shaded}

\section*{Missing values}\label{missing-values}
\addcontentsline{toc}{section}{Missing values}

\markright{Missing values}

Missing data is written \texttt{NA}, and it is contagious by design.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{pop }\OtherTok{\textless{}{-}} \FunctionTok{c}\NormalTok{(}\DecValTok{12}\NormalTok{, }\DecValTok{45}\NormalTok{, }\ConstantTok{NA}\NormalTok{, }\DecValTok{8}\NormalTok{)}
\FunctionTok{mean}\NormalTok{(pop)}
\CommentTok{\#\textgreater{} [1] NA}
\end{Highlighting}
\end{Shaded}

R is telling you something true: the mean of a set that includes an
unknown value is unknown. If you are content to ignore the missing case,
say so explicitly.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{mean}\NormalTok{(pop, }\AttributeTok{na.rm =} \ConstantTok{TRUE}\NormalTok{)}
\CommentTok{\#\textgreater{} [1] 21.66667}
\end{Highlighting}
\end{Shaded}

Say so deliberately rather than reflexively. Dropping missing cases is a
substantive decision about your sample, and the final project asks you
to make such decisions visible rather than silent.

To find them:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{is.na}\NormalTok{(pop)}
\CommentTok{\#\textgreater{} [1] FALSE FALSE  TRUE FALSE}

\FunctionTok{sum}\NormalTok{(}\FunctionTok{is.na}\NormalTok{(pop))}
\CommentTok{\#\textgreater{} [1] 1}
\end{Highlighting}
\end{Shaded}

\section*{Data frames}\label{data-frames}
\addcontentsline{toc}{section}{Data frames}

\markright{Data frames}

A data frame is a table: several vectors of equal length standing side
by side as columns, each with a name, each with its own type. This is
what a political science dataset is.

Load one. The \texttt{read.csv()} function accepts a web address
directly, so nothing needs downloading.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"https://raw.githubusercontent.com/babakrezaee/AppliedAI{-}PoliSci/main/data/FearonLaitin2003.csv"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

These are the data behind Fearon and Laitin's 2003 article on ethnicity,
insurgency, and civil war, one of the most cited studies in the conflict
literature. The unit of analysis is the country-year, and we will return
to it in Week 6.

\section*{Look before you calculate}\label{look-before-you-calculate}
\addcontentsline{toc}{section}{Look before you calculate}

\markright{Look before you calculate}

Before doing anything with a new dataset, find out what you have.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{dim}\NormalTok{(fl)          }\CommentTok{\# rows and columns}
\FunctionTok{nrow}\NormalTok{(fl)}
\FunctionTok{names}\NormalTok{(fl)        }\CommentTok{\# column names}
\FunctionTok{head}\NormalTok{(fl, }\AttributeTok{n =} \DecValTok{3}\NormalTok{)  }\CommentTok{\# first three rows}
\FunctionTok{str}\NormalTok{(fl)          }\CommentTok{\# structure: every column, its type, first few values}
\end{Highlighting}
\end{Shaded}

\texttt{str()} is the most useful of these, because it reports the type
of every column. A numeric variable that arrived as text will announce
itself here rather than three steps later.

For a single variable, \texttt{summary()} gives the distribution and,
importantly, the count of missing values.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{summary}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{gdpen)}
\end{Highlighting}
\end{Shaded}

The dollar sign extracts one column by name. It is the workhorse of base
R and you will use it constantly.

\section*{An example of why you look
first}\label{an-example-of-why-you-look-first}
\addcontentsline{toc}{section}{An example of why you look first}

\markright{An example of why you look first}

The outcome variable in these data is \texttt{onset}, coded one in a
country-year when a civil war begins and zero otherwise. Count its
values.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{table}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{onset)}
\end{Highlighting}
\end{Shaded}

You will find a handful of zeros and ones, as expected, and also a
single observation coded \texttt{4}. That is a data entry error, present
in the distributed file, and it has survived into a great many
replications.

It matters. A model fitted with \texttt{onset} treated as numeric would
take that four seriously. Left as a factor with three levels, a
classifier would try to predict a category that occurs once in six
thousand cases. Either way the result is wrong in a manner no error
message will announce.

The fix is one line.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl}\SpecialCharTok{$}\NormalTok{onset[fl}\SpecialCharTok{$}\NormalTok{onset }\SpecialCharTok{\textgreater{}} \DecValTok{1}\NormalTok{] }\OtherTok{\textless{}{-}} \DecValTok{1}
\FunctionTok{table}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{onset)}
\end{Highlighting}
\end{Shaded}

The lesson generalizes beyond this dataset. Run \texttt{table()} on
every categorical variable and \texttt{summary()} on every numeric one
before you model anything. It takes two minutes and it is the cheapest
error-catching you will ever do.

\section*{Selecting rows and columns}\label{selecting-rows-and-columns}
\addcontentsline{toc}{section}{Selecting rows and columns}

\markright{Selecting rows and columns}

Data frames take two indices inside the brackets, rows first and columns
second.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl[}\DecValTok{1}\NormalTok{, ]            }\CommentTok{\# first row, all columns}
\NormalTok{fl[, }\StringTok{"onset"}\NormalTok{]      }\CommentTok{\# the onset column}
\NormalTok{fl[}\DecValTok{1}\SpecialCharTok{:}\DecValTok{5}\NormalTok{, }\FunctionTok{c}\NormalTok{(}\StringTok{"country"}\NormalTok{, }\StringTok{"year"}\NormalTok{, }\StringTok{"onset"}\NormalTok{)]}
\end{Highlighting}
\end{Shaded}

To keep rows meeting a condition:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{africa }\OtherTok{\textless{}{-}}\NormalTok{ fl[fl}\SpecialCharTok{$}\NormalTok{ssafrica }\SpecialCharTok{==} \DecValTok{1}\NormalTok{, ]}
\FunctionTok{nrow}\NormalTok{(africa)}
\end{Highlighting}
\end{Shaded}

Note the double equals sign. A single \texttt{=} assigns; a double
\texttt{==} asks whether two things are equal. Mixing them up is a rite
of passage.

\section*{The tidyverse, and the pipe}\label{the-tidyverse-and-the-pipe}
\addcontentsline{toc}{section}{The tidyverse, and the pipe}

\markright{The tidyverse, and the pipe}

Base R can do everything above, and for many tasks the tidyverse offers
a version that reads more like a sentence. Install it once, then load it
in each session.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# install.packages("tidyverse")   \# once, ever}
\FunctionTok{library}\NormalTok{(tidyverse)                }\CommentTok{\# every session}
\end{Highlighting}
\end{Shaded}

The pipe operator \texttt{\%\textgreater{}\%} takes whatever is on its
left and passes it as the first argument to the function on its right.
Written this way, a chain of operations reads in the order it happens.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{filter}\NormalTok{(ssafrica }\SpecialCharTok{==} \DecValTok{1}\NormalTok{, year }\SpecialCharTok{\textgreater{}=} \DecValTok{1980}\NormalTok{) }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{select}\NormalTok{(country, year, onset, gdpen) }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{head}\NormalTok{()}
\end{Highlighting}
\end{Shaded}

Compare that with the base R equivalent, which has to be read from the
inside out:

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{head}\NormalTok{(fl[fl}\SpecialCharTok{$}\NormalTok{ssafrica }\SpecialCharTok{==} \DecValTok{1} \SpecialCharTok{\&}\NormalTok{ fl}\SpecialCharTok{$}\NormalTok{year }\SpecialCharTok{\textgreater{}=} \DecValTok{1980}\NormalTok{, }\FunctionTok{c}\NormalTok{(}\StringTok{"country"}\NormalTok{, }\StringTok{"year"}\NormalTok{, }\StringTok{"onset"}\NormalTok{, }\StringTok{"gdpen"}\NormalTok{)])}
\end{Highlighting}
\end{Shaded}

Both are correct. The piped version is easier to modify six weeks later,
which is why the handouts use it. In RStudio, \textbf{Cmd and Shift and
M} on a Mac, or \textbf{Ctrl and Shift and M} on Windows, types the
pipe.

Three verbs will carry most of your work. \texttt{filter()} keeps rows,
\texttt{select()} keeps columns, and \texttt{mutate()} creates new ones.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{filter}\NormalTok{(}\SpecialCharTok{!}\FunctionTok{is.na}\NormalTok{(gdpen)) }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{mutate}\NormalTok{(}\AttributeTok{log\_pop =} \FunctionTok{log}\NormalTok{(pop)) }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{select}\NormalTok{(country, year, gdpen, log\_pop) }\SpecialCharTok{\%\textgreater{}\%}
  \FunctionTok{head}\NormalTok{()}
\end{Highlighting}
\end{Shaded}

\section*{Factors}\label{factors}
\addcontentsline{toc}{section}{Factors}

\markright{Factors}

A factor is R's type for a categorical variable: values drawn from a
fixed set of levels. Modeling functions expect categorical outcomes as
factors, so you will convert deliberately.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl}\SpecialCharTok{$}\NormalTok{onset }\OtherTok{\textless{}{-}} \FunctionTok{factor}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{onset)}
\FunctionTok{levels}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{onset)}
\CommentTok{\#\textgreater{} [1] "0" "1"}
\end{Highlighting}
\end{Shaded}

One warning worth carrying. Converting a factor straight to numeric
returns the level codes, not the labels, so a factor with levels ``0''
and ``1'' becomes 1 and 2. If you need the underlying numbers, route
through character first.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{as.numeric}\NormalTok{(}\FunctionTok{as.character}\NormalTok{(fl}\SpecialCharTok{$}\NormalTok{onset))}
\end{Highlighting}
\end{Shaded}

\section*{Matrices, briefly}\label{matrices-briefly}
\addcontentsline{toc}{section}{Matrices, briefly}

\markright{Matrices, briefly}

A matrix is a rectangle of values that are all the same type, which is
the difference from a data frame. You will not build many, but they
appear inside modeling functions, and older code uses \texttt{cbind()}
and \texttt{rbind()} to assemble them.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{m }\OtherTok{\textless{}{-}} \FunctionTok{matrix}\NormalTok{(}\FunctionTok{c}\NormalTok{(}\DecValTok{2}\NormalTok{, }\DecValTok{4}\NormalTok{, }\DecValTok{3}\NormalTok{, }\DecValTok{1}\NormalTok{, }\DecValTok{5}\NormalTok{, }\DecValTok{7}\NormalTok{), }\AttributeTok{nrow =} \DecValTok{3}\NormalTok{, }\AttributeTok{ncol =} \DecValTok{2}\NormalTok{)}
\NormalTok{m}
\FunctionTok{t}\NormalTok{(m)               }\CommentTok{\# transpose}
\FunctionTok{cbind}\NormalTok{(m, }\FunctionTok{c}\NormalTok{(}\DecValTok{7}\NormalTok{, }\DecValTok{4}\NormalTok{, }\DecValTok{2}\NormalTok{))  }\CommentTok{\# add a column}
\end{Highlighting}
\end{Shaded}

Recognizing them is enough for now. Week 4 returns to matrices when text
becomes a document-term matrix.

\section*{Getting help}\label{getting-help}
\addcontentsline{toc}{section}{Getting help}

\markright{Getting help}

Every function has a help page, reachable with a question mark.

\chapter*{Projects, Paths, and Reproducible
Habits}\label{projects-paths-and-reproducible-habits}
\addcontentsline{toc}{chapter}{Projects, Paths, and Reproducible Habits}

\markboth{Projects, Paths, and Reproducible Habits}{Projects, Paths, and
Reproducible Habits}

Code that runs on your machine and code that runs are not the same
thing. The gap between them is where most of the marks on your final
project's reproducibility criterion are lost, and almost all of it comes
down to a handful of habits that cost nothing once you have them.

This chapter is about those habits. None of the material is difficult.
What makes it worth a chapter is that the failures it prevents do not
appear until the moment they are most expensive, which is when someone
else opens your work.

\section*{The problem, stated plainly}\label{the-problem-stated-plainly}
\addcontentsline{toc}{section}{The problem, stated plainly}

\markright{The problem, stated plainly}

Suppose you write this at the top of an analysis.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{setwd}\NormalTok{(}\StringTok{"/Users/babak/Documents/AI course/week 4/analysis"}\NormalTok{)}
\FunctionTok{read.csv}\NormalTok{(}\StringTok{"civil\_war.csv"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

On your laptop, in that folder, it works. Everywhere else it fails,
because no other computer has that folder. Your instructor does not have
it, your co-author or colleague does not have it, and neither will you
after you reorganize your files in March.

\texttt{setwd()} is the most common single reason a submitted document
does not run. You will see it constantly in older code, including in
tutorials and in published replication files, and the instinct to copy
it is understandable. Do not. Nothing in this course requires it, and
using it may cost you points on the project.

The replacement is not a different function. It is a different way of
organizing work.

\section*{R Projects}\label{r-projects}
\addcontentsline{toc}{section}{R Projects}

\markright{R Projects}

An R Project is a folder that R treats as the home of a piece of work.
Creating one puts a small file with the extension \texttt{.Rproj} inside
the folder, and from then on, opening that file does three useful things
at once: it starts a fresh R session, it sets the working directory to
that folder, and it remembers which files you had open.

That second point is the whole trick. Because the working directory is
already correct, you never have to set it, and because it is set
relative to the project rather than to your machine, the same code works
on anyone else's computer.

To create one: \textbf{File \textgreater{} New Project \textgreater{}
New Directory \textgreater{} New Project}, then give the folder a name
and a location. For work you already have in a folder, use \textbf{File
\textgreater{} New Project \textgreater{} Existing Directory} instead.

From then on, open the project by double-clicking the \texttt{.Rproj}
file rather than by opening a script directly. If you open a
\texttt{.qmd} from the Finder, R starts with no project and the paths
will not resolve, which produces a ``cannot open file'' error that looks
like a problem with the file and is not.

\section*{Relative paths}\label{relative-paths}
\addcontentsline{toc}{section}{Relative paths}

\markright{Relative paths}

Inside a project, you refer to files by their location relative to the
project folder, with no leading slash and no drive letter.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"data/civil\_war.csv"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

That line means ``the file \texttt{civil\_war.csv}, inside a folder
called \texttt{data}, inside whatever folder this project lives in.'' It
is true on every machine.

A few conventions worth following:

\begin{itemize}
\tightlist
\item
  Forward slashes, \texttt{/}, on every operating system, including
  Windows. R accepts them everywhere.
\item
  No spaces in file or folder names. Use \texttt{civil\_war.csv} rather
  than \texttt{civil\ war.csv}. Spaces are legal, but they will
  eventually bite you.
\item
  Lower case, consistently. Some systems treat \texttt{Data/} and
  \texttt{data/} as the same folder and some do not.
\end{itemize}

\section*{A layout that works}\label{a-layout-that-works}
\addcontentsline{toc}{section}{A layout that works}

\markright{A layout that works}

You do not need an elaborate structure. This is enough for the final
project and it will still make sense a year from now.

\begin{verbatim}
YourProject/
  YourProject.Rproj
  analysis.qmd          the document you submit
  data/
    raw/                exactly as downloaded, never edited
    processed/          anything your code produced
  R/
    clean-data.R        scripts that do a job
  figures/              plots your code saved
\end{verbatim}

The distinction between \texttt{data/raw/} and \texttt{data/processed/}
is the one that earns its keep. Raw files are never opened in Excel and
never edited by hand. Every change is made in code, which means every
change is visible, reversible, and explicable when a reviewer,
instructor, or colleague asks why your sample has 4,318 rows rather than
4,502.

\addcontentsline{toc}{section}{Note on this course}

\markright{Note on this course}

The handouts here load their data straight from a web address, so there
are no local files to find.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"https://raw.githubusercontent.com/babakrezaee/AppliedAI{-}PoliSci/main/data/FearonLaitin2003.csv"}\NormalTok{)}
\end{Highlighting}

\section*{Never save the workspace}\label{never-save-the-workspace}
\addcontentsline{toc}{section}{Never save the workspace}

\markright{Never save the workspace}

By default, R offers to save your objects when you quit and to reload
them when you return. Turn this off.

\textbf{Tools \textgreater{} Global Options \textgreater{} General},
then set \textbf{Save workspace to .RData on exit} to \textbf{Never},
and untick \textbf{Restore .RData into workspace at startup}.

The reason is that a restored workspace hides broken code. An object
created three weeks ago by a line you have since deleted is still
sitting in memory, so your analysis appears to work while depending on
something that no longer exists anywhere in your files. The failure
surfaces when you knit, or when someone else runs it, which is exactly
the wrong time.

Your objects should always be recreatable by running your code. If they
are not, the code is incomplete.

\section*{Restart, and run from clean}\label{restart-and-run-from-clean}
\addcontentsline{toc}{section}{Restart, and run from clean}

\markright{Restart, and run from clean}

The companion habit is to restart R often. \textbf{Session
\textgreater{} Restart R}, or \textbf{Cmd and Shift and F10} on a Mac,
\textbf{Ctrl and Shift and F10} on Windows.

After restarting, run your document from the top. If it completes, it
works. If it does not, you have found a dependency on something that
existed only in your session, and you have found it now rather than the
night before a deadline.

Do this before every submission, without exception. It is the entire
test, and it takes under a minute.

\section*{Packages}\label{packages}
\addcontentsline{toc}{section}{Packages}

\markright{Packages}

Load every package you use at the top of the document, in one place.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{library}\NormalTok{(tidyverse)}
\FunctionTok{library}\NormalTok{(caret)}
\end{Highlighting}
\end{Shaded}

\textbf{Do not put \texttt{install.packages()} in a document you
submit.} Installation is something you do once on your own machine, from
the console. Left in a document, it re-installs packages on the reader's
computer, which is slow, occasionally destructive, and never what they
wanted.

If a package is missing, the reader gets a clear error naming it, which
is the correct outcome. A short note in your README saying which
packages the project needs is a courtesy worth extending.

\section*{Seeds}\label{seeds}
\addcontentsline{toc}{section}{Seeds}

\markright{Seeds}

Anything involving randomness, which in this course means splitting data
into training and test sets, sampling, and fitting a random forest,
gives a different answer each time it runs.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{set.seed}\NormalTok{(}\DecValTok{7}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

Put that line near the top, once, before anything random happens. The
number itself is arbitrary and does not matter. What matters is that
with it, your reported numbers reproduce exactly, and without it, a
reader who runs your code gets results that disagree with your text for
no stated reason.

\section*{When a path fails anyway}\label{when-a-path-fails-anyway}
\addcontentsline{toc}{section}{When a path fails anyway}

\markright{When a path fails anyway}

The error will look like this.

\begin{verbatim}
Warning: cannot open file 'data/civil_war.csv': No such file or directory
Error in file(file, "rt") : cannot open the connection
\end{verbatim}

Three checks, in order.

\textbf{Where does R think it is?}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{getwd}\NormalTok{()}
\end{Highlighting}
\end{Shaded}

If that is not your project folder, you opened the file without opening
the project. Close everything and open the \texttt{.Rproj} file.

\textbf{Does R see the file?}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{list.files}\NormalTok{(}\StringTok{"data"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

If the file is not listed, the problem is the name or the location, not
the code.

\textbf{Is the name exactly right?} Capital letters count. So does the
extension, and macOS hides extensions by default, so a file that looks
like \texttt{civil\_war.csv} in the Finder may actually be
\texttt{civil\_war.csv.txt}.

Notice that the fix is never \texttt{setwd()}.

\chapter*{Reading Data into R}\label{reading-data-into-r}
\addcontentsline{toc}{chapter}{Reading Data into R}

\markboth{Reading Data into R}{Reading Data into R}

Importing data feels like the trivial step before the real work, and it
is where a surprising share of analytical errors are born. The reason is
that R almost never refuses to import a file. It makes a decision about
what your data mean, tells you nothing, and carries on. A column of
numbers arrives as text, a missing value code of \texttt{-99} is treated
as a real observation, and everything downstream is quietly wrong.

This chapter covers the formats you will actually meet and, more
importantly, the check that catches the failures.

\section*{CSV, the ordinary case}\label{csv-the-ordinary-case}
\addcontentsline{toc}{section}{CSV, the ordinary case}

\markright{CSV, the ordinary case}

A comma-separated (CSV) file is plain text with one row per line and
commas between fields. It is the format most political science data
arrive in, and R reads it out of the box.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"data/FearonLaitin2003.csv"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

There is also a tidyverse version, \texttt{read\_csv()}, with an
underscore rather than a period.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{library}\NormalTok{(tidyverse)}
\NormalTok{fl }\OtherTok{\textless{}{-}} \FunctionTok{read\_csv}\NormalTok{(}\StringTok{"data/FearonLaitin2003.csv"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

Three differences matter in practice. \texttt{read\_csv()} is faster on
large files, it prints a summary of the column types it guessed, which
is useful information rather than clutter, and it returns a tibble
rather than a data frame. A tibble is a data frame with better printing
behavior, and everything you learned in the previous chapter applies to
it unchanged.

Either is acceptable in this course. The handouts use
\texttt{read.csv()} because it needs no package, so the first line of a
chapter always runs.

\section*{Straight from a web
address}\label{straight-from-a-web-address}
\addcontentsline{toc}{section}{Straight from a web address}

\markright{Straight from a web address}

Both functions accept a URL wherever they accept a filename, which means
data can be loaded with nothing downloaded.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{fl }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"https://raw.githubusercontent.com/babakrezaee/AppliedAI{-}PoliSci/main/data/FearonLaitin2003.csv"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

This is how every dataset in these handouts is loaded. It has two
advantages worth naming: the code runs identically on any machine, and
there is no file path to get wrong.

It has one disadvantage. If the address ever changes, the code stops
working, and if the file behind the address is edited, your results
change without your knowing. For the final project, download the file
once and put it on your cloud-based platform, then you have control over
your data source than relying on someone else's server.

Note the address on Github must be the \textbf{raw} one. Clicking a CSV
on GitHub shows a formatted preview page, and its address returns HTML
rather than data. The \textbf{Raw} button gives the address you want,
and it always begins \texttt{raw.githubusercontent.com}. You can also
upload your files on Dropbox, Googledrive, and Onedrive; just make sure
that you have the permission to put the files on these public
cloud-based platforms.

\section*{Check the import, every
time}\label{check-the-import-every-time}
\addcontentsline{toc}{section}{Check the import, every time}

\markright{Check the import, every time}

This is the habit the chapter exists for. Three lines, immediately after
loading anything.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{dim}\NormalTok{(fl)}
\FunctionTok{str}\NormalTok{(fl)}
\FunctionTok{summary}\NormalTok{(fl)}
\end{Highlighting}
\end{Shaded}

You are looking for three things.

\textbf{Did every column get the type you expected?} A numeric variable
listed as \texttt{chr} in the \texttt{str()} output has a non-numeric
value hiding in it somewhere.

\textbf{Are the row and column counts right?} If the file should have
6,610 rows and you have 6,609, the header row was probably read as data,
or the last line lacks a line break.

\textbf{Do the ranges make sense?} \texttt{summary()} reports the
minimum and maximum of each numeric column. A \texttt{polity2} score of
\texttt{-88} or a population of \texttt{-99} is a missing value code,
not an observation, and it will wreck any model that takes it seriously.

\section*{Missing value codes}\label{missing-value-codes}
\addcontentsline{toc}{section}{Missing value codes}

\markright{Missing value codes}

Older datasets frequently encode missing values as numbers, with
\texttt{-99}, \texttt{-999}, and \texttt{-88} being the common choices.
R has no way of knowing this and will treat them as real.

Tell it explicitly at import.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"data/survey.csv"}\NormalTok{, }\AttributeTok{na.strings =} \FunctionTok{c}\NormalTok{(}\StringTok{"NA"}\NormalTok{, }\StringTok{""}\NormalTok{, }\StringTok{"{-}99"}\NormalTok{, }\StringTok{"{-}999"}\NormalTok{))}
\end{Highlighting}
\end{Shaded}

Or fix it afterward, which is clearer when only some columns are
affected.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat}\SpecialCharTok{$}\NormalTok{income[dat}\SpecialCharTok{$}\NormalTok{income }\SpecialCharTok{==} \SpecialCharTok{{-}}\DecValTok{99}\NormalTok{] }\OtherTok{\textless{}{-}} \ConstantTok{NA}
\end{Highlighting}
\end{Shaded}

Either way, do it before anything else. A mean computed over a column
containing \texttt{-99} is not slightly wrong, it is meaningless, and
nothing in the output will tell you.

\section*{When the commas are not
commas}\label{when-the-commas-are-not-commas}
\addcontentsline{toc}{section}{When the commas are not commas}

\markright{When the commas are not commas}

Files exported from Excel on a European system are often separated by
semicolons rather than commas, and they use commas as decimal points.
Opening one with \texttt{read.csv()} produces a single column of text.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read.csv2}\NormalTok{(}\StringTok{"data/dutch\_export.csv"}\NormalTok{)   }\CommentTok{\# semicolons, comma decimals}
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read\_csv2}\NormalTok{(}\StringTok{"data/dutch\_export.csv"}\NormalTok{)   }\CommentTok{\# tidyverse equivalent}
\end{Highlighting}
\end{Shaded}

Worth knowing here rather than elsewhere, since Dutch-locale Excel does
this by default and several of you will hit it with data you export
yourselves.

If the separator is something else entirely, such as a tab, say so:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read.delim}\NormalTok{(}\StringTok{"data/file.txt"}\NormalTok{)                    }\CommentTok{\# tab separated}
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"data/file.txt"}\NormalTok{, }\AttributeTok{sep =} \StringTok{"|"}\NormalTok{)           }\CommentTok{\# anything else}
\end{Highlighting}
\end{Shaded}

The fastest way to diagnose any of this is to open the file in a plain
text editor and look at the first two lines. Two minutes of looking
beats an hour of guessing.

\section*{Accented characters}\label{accented-characters}
\addcontentsline{toc}{section}{Accented characters}

\markright{Accented characters}

Country names, party names, and any text data will contain characters
outside plain English. If they arrive mangled, as \texttt{Ã©} where
\texttt{é} belongs, the file's encoding was misread.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read.csv}\NormalTok{(}\StringTok{"data/parties.csv"}\NormalTok{, }\AttributeTok{encoding =} \StringTok{"UTF{-}8"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

UTF-8 is correct for the large majority of files you will meet. This
will matter in Week 4, when text becomes data.

\section*{Excel files}\label{excel-files}
\addcontentsline{toc}{section}{Excel files}

\markright{Excel files}

Excel files are not text and cannot be read by \texttt{read.csv()}. Use
\texttt{readxl}.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# install.packages("readxl")}
\FunctionTok{library}\NormalTok{(readxl)}

\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read\_excel}\NormalTok{(}\StringTok{"data/data.xlsx"}\NormalTok{)}
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read\_excel}\NormalTok{(}\StringTok{"data/data.xlsx"}\NormalTok{, }\AttributeTok{sheet =} \StringTok{"Coding"}\NormalTok{)   }\CommentTok{\# a named sheet}
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read\_excel}\NormalTok{(}\StringTok{"data/data.xlsx"}\NormalTok{, }\AttributeTok{skip =} \DecValTok{3}\NormalTok{)           }\CommentTok{\# skip title rows}
\end{Highlighting}
\end{Shaded}

\texttt{skip} earns its place. Spreadsheets kept by humans very often
carry a title, a blank line, and a note before the actual header row,
and without \texttt{skip} all of that is read as data.

A note on Excel more generally. It is a reasonable place to receive data
and a poor place to edit it, because changes made by hand leave no
record. If a value must change, change it in R, where the change is
visible in your code and reversible.

\section*{Stata and SPSS}\label{stata-and-spss}
\addcontentsline{toc}{section}{Stata and SPSS}

\markright{Stata and SPSS}

Political science data arrive as \texttt{.dta} and \texttt{.sav} more
often than anyone would like. The \texttt{haven} package reads both.

\begin{Shaded}
\begin{Highlighting}[]
\CommentTok{\# install.packages("haven")}
\FunctionTok{library}\NormalTok{(haven)}

\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read\_dta}\NormalTok{(}\StringTok{"data/anes.dta"}\NormalTok{)   }\CommentTok{\# Stata}
\NormalTok{dat }\OtherTok{\textless{}{-}} \FunctionTok{read\_sav}\NormalTok{(}\StringTok{"data/ess.sav"}\NormalTok{)    }\CommentTok{\# SPSS}
\end{Highlighting}
\end{Shaded}

Older tutorials recommend \texttt{foreign} and \texttt{Hmisc} for this.
Both still work, and \texttt{haven} handles recent file versions and
preserves variable labels better, so prefer it.

Labelled columns from these formats sometimes behave unexpectedly in
models. If one gives you trouble, strip the labels:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{dat}\SpecialCharTok{$}\NormalTok{party }\OtherTok{\textless{}{-}}\NormalTok{ haven}\SpecialCharTok{::}\FunctionTok{zap\_labels}\NormalTok{(dat}\SpecialCharTok{$}\NormalTok{party)}
\end{Highlighting}
\end{Shaded}

\section*{Saving}\label{saving}
\addcontentsline{toc}{section}{Saving}

\markright{Saving}

To hand data to someone who may not use R, write a CSV.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{write.csv}\NormalTok{(dat, }\StringTok{"data/processed/cleaned.csv"}\NormalTok{, }\AttributeTok{row.names =} \ConstantTok{FALSE}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

\texttt{row.names\ =\ FALSE} matters. Without it, R adds a column of row
numbers, and a file that is written and read a few times accumulates
several of them.

To save an R object for your own later use, including model objects and
anything else a CSV cannot hold, use \texttt{saveRDS()}.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{saveRDS}\NormalTok{(model, }\StringTok{"output/model.rds"}\NormalTok{)}
\NormalTok{model }\OtherTok{\textless{}{-}} \FunctionTok{readRDS}\NormalTok{(}\StringTok{"output/model.rds"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

This is worth knowing for the final project, or algorithms that take a
longer time to run, such as Random Forest. A model that takes several
minutes to fit can be fitted once, saved, and read back, so that
re-rendering the document does not refit it.

\chapter{Prediction, Causation, and the Vocabulary of
AI}\label{prediction-causation-and-the-vocabulary-of-ai}

\emph{Week 1, 2 September}

This first session has two purposes. First, we need to distinguish
between correlation, causation, prediction, and forecasting. These are
related, but they are not the same research goal, and confusing them can
produce bad research. Second, we need a working vocabulary for talking
about artificial intelligence. Terms such as machine learning,
generative AI, reasoning model, and agent are often used as though they
refer to the same thing. They do not.

There is no code in this handout. The work this week is conceptual. That
may sound less exciting than fitting a model, but it matters. A model
can be technically impressive and still answer the wrong question. The
same problem appears in public debates about AI, where a loose use of
one term can hide who designed a system, what it actually does, and who
is responsible when it fails.

Developing a theoretical argument about a political phenomenon is work
you do across the programme. This course adds three things to it. We ask
how evidence can be used to evaluate an argument. We ask how statistical
and machine-learning models can be used to anticipate outcomes. And we
treat AI systems themselves as objects of political analysis, because
they are increasingly part of how states, parties, platforms, and
administrations act.

\section{What kind of question are we
asking?}\label{what-kind-of-question-are-we-asking}

Political scientists use qualitative, quantitative, and mixed-method
research designs. All three can be empirical, and they share an
underlying scientific principle: theoretical claims should be exposed to
evidence that could count against them.

For Popper, a theory is scientific when it produces claims that are
empirically testable and open to falsification. This does not mean that
one study can prove a theory. Evidence can support a hypothesis without
proving that it is true. That support remains provisional and depends on
the quality of the research design, the measurement, and the
alternatives that have been considered.

Lakatos asks us to look beyond the fate of one hypothesis and consider
the development of a research programme (Lakatos 1970). Does it generate
new expectations and improve our understanding, or does it survive only
because its supporters keep adding qualifications after every failure?
We will return to this question when we compare models: improving
performance is useful, but adding complexity without learning anything
substantive is not necessarily scientific progress.

The same care is needed when discussing null hypotheses. Rejecting a
null hypothesis can provide support for a substantive alternative.
Failing to reject a null hypothesis is also evidence from the study and
can be informative, particularly when the design is strong and the test
has adequate power. It does not prove the null hypothesis. More
generally, when observations remain consistent with the implications of
a theory, we may describe this as empirical support, not as final
confirmation.

Publishing research is therefore an invitation to other scholars to
attack the argument scientifically: to examine the assumptions, repeat
the analysis, use other data, and try to show that the finding does not
hold.

\subsection{Correlation}\label{correlation}

Sometimes our research is descriptive. We want to know whether two
variables are associated and how strong that association is. Descriptive
and correlational research has sometimes been downplayed following the
causal-inference revolution in economics and political science. That is
unfortunate. Description is often the first step in bringing a new
political phenomenon into view, and a reliable pattern can be important
even before its cause is established.

Consider the long-standing debate about economic development and
democracy. There is a well-known association between them: wealthier
countries tend, on average, to be more democratic. But that association
does not tell us which way the causal arrow runs. Economic development
may encourage democratization. Democracy may contribute to economic
development. A third factor may affect both, or the relationship may run
in both directions.

We can present the distinction schematically:

\textbf{Correlation}

\[Economic~development \overset{?; +/-}{\longleftrightarrow} Political~development\]

\textbf{Possible causal relationships}

\[Economic~development \overset{+/-}{\longrightarrow} Political~development\]

\[Economic~development \overset{+/-}{\longleftarrow} Political~development\]

The correlation is a finding. The arrows are additional claims that
require additional evidence.

\subsection{Causation}\label{causation}

A causal study needs an identification strategy: an argument about why
the estimated relationship can be interpreted as the effect of \(X\) on
\(Y\), rather than as selection, reverse causation, measurement error,
or the influence of an omitted factor. Calling \(X\) an independent
variable does not automatically make it exogenous. Exogeneity is an
assumption that must be defended through the design.

Bias is also worth defining carefully. In statistical terms, an
estimator is biased when its expected value differs systematically from
the parameter it is intended to estimate. This is not the same as
finding that one estimate is statistically significant. Omitted
variables, selection, and measurement problems are among the reasons an
estimate may fail to recover the causal quantity we care about.

\subsubsection{The experimental ideal}\label{the-experimental-ideal}

Randomized experiments provide a particularly clear identification
strategy. In one of my research projects, I examined whether information
about the principles of nonviolent resistance changes attitudes toward
this form of political action. Participants were randomly assigned to
two groups. One group watched a clip about International Relations. The
other watched a clip about nonviolent resistance. I then compared their
average attitudes after the intervention.

Random assignment means that treatment status is independent of
participants' pre-treatment characteristics by design. Across repeated
random assignments, the groups are comparable on average. In one
realized experiment, however, the groups do not have to be perfectly
identical on every characteristic. Covariate summaries can help us
describe the sample and identify surprising imbalances, but they do not
make the assignment random; the assignment procedure does that.

The comparison between the two groups gives us an estimate of the
average effect of receiving the information in that study. Notice how
much work the design is doing. The difference in outcomes becomes
interpretable because the intervention was assigned, rather than
selected by participants.

\subsubsection{Observational data}\label{observational-data}

Political scientists often cannot conduct experiments. Think about
conflict research. Can we randomly assign some countries to civil war
and others to peace in order to study the economic consequences? Of
course not.

We therefore rely on observational data produced by political and social
processes that we do not control. If we want to estimate the effect of
democracy on economic development, countries are not assigned randomly
to different levels of democracy. Democratic countries may also have
stronger state institutions, more secure property rights, different
colonial histories, or other characteristics that affect economic
performance.

Adding observed confounders to a model may reduce some of these
problems, but it does not automatically solve them. Matching,
instrumental variables, regression discontinuity, panel designs, and
other methods can support an identification strategy under particular
assumptions. Developing those strategies is outside the scope of this
course. Recognizing when a claim requires one is not.

\subsection{Prediction}\label{prediction}

Prediction changes the question. Given what we know about a case, how
accurately can we estimate its outcome?

Suppose we want to predict civil-war onset. Income, terrain, state
capacity, political institutions, conflict history, and regional
conditions may all carry useful information. A predictive model combines
that information and is evaluated by how well it performs on cases it
did not use for fitting.

This is different from estimating the causal effect of one variable. A
model may predict well even when some of its inputs are only proxies.
Imagine a bank using postal code to predict loan default. Postal code
may carry information about income, employment, housing, and ethnicity.
It can therefore be useful for prediction without providing a causal
explanation of why a person defaults. Intervening on the postal code
would not necessarily change the outcome.

Shmueli distinguishes explanatory modeling from predictive modeling
(Shmueli 2010). Cranmer and Desmarais argue that political science has
paid too little attention to predictive performance (Cranmer and
Desmarais 2017). Hofman, Sharma, and Watts make a related case for
taking prediction more seriously when evaluating explanations of social
phenomena (Hofman et al. 2017). None of this means that accuracy should
replace theory or causal identification.

Predictive performance can discipline an explanation. If an account
repeatedly fails to anticipate the phenomenon it claims to explain, we
have reason to examine it more closely. But predictive performance is
not the same thing as causal evidence, and strong prediction is not
sufficient for a good explanation. Social outcomes can also contain
substantial noise, which means that a credible causal explanation will
not always generate highly accurate individual predictions.

The purpose of the model therefore matters. If the task is prediction,
performance on unseen cases is central. Flexible functional forms may be
useful even when no single coefficient provides a simple substantive
interpretation. If the task is causal inference, good test-set accuracy
does not rescue a weak identification strategy.

\subsection{Forecasting}\label{forecasting}

Forecasting asks about outcomes that have not happened yet.

Suppose we have housing-price data from 1990 to 2026. We fit a model
using observations from 1990 to 2019 and test it on sales from 2020 to
2026. When the model estimates the price of a house sold in 2023, it is
making a prediction for a case whose outcome was hidden from the model
but is already known to us. We can calculate the error immediately.

If we use the same model to estimate prices in 2027 or 2028, we are
forecasting. The outcomes do not yet exist, so the forecast cannot be
fully evaluated until time passes.

When forecasting is the goal, we normally divide training and test data
by time rather than at random. A random split could allow a model
trained on 2025 observations to predict an outcome from 2010. That may
be acceptable for some prediction tasks, but it does not simulate the
information problem faced by someone trying to anticipate the future.

A temporal test set is still not a genuine forecast. It is a simulation
of forecasting using outcomes that are already known to the researcher.
It tells us how the model would have performed in a previous period. It
cannot guarantee that relationships will remain stable when the model is
used later. Early-warning systems such as ViEWS ({Hegre et al.} 2019)
produce forecasts in real time and can be fully judged only after the
forecast period has passed.

\section{Why does confusing these goals produce bad
research?}\label{why-does-confusing-these-goals-produce-bad-research}

There are several common mistakes.

\textbf{Causal language after a predictive model.} High accuracy shows
that the predictors contain information about the outcome. It does not
show that intervening on one of them would change the outcome. A random
forest does not turn an association into a causal effect.

\textbf{Predictive claims from a causal design.} A well-identified
estimate of one causal effect may be a poor predictor of the outcome as
a whole. The design was built to isolate an effect, not necessarily to
anticipate every case.

\textbf{Treating test-set performance as demonstrated forecast
performance.} Good performance on held-out historical years is useful
evidence. It is not proof that the model will work next year,
particularly when political conditions change.

\textbf{Applying the wrong evaluation standard.} Predictive models are
sometimes dismissed because they do not have easily interpretable
coefficients. Causal estimates are sometimes dismissed because they have
a low \(R^2\). Neither criticism is automatically relevant. We first
need to know what the model was built to do.

\section{What is under the hood of
AI?}\label{what-is-under-the-hood-of-ai}

For many contemporary AI systems, machine learning is the motor under
the hood. Credit scoring, content moderation, fraud detection,
political-text classification, recommendation systems, and large
language models all rely heavily on models fitted to data.

AI is nevertheless broader than machine learning. Some systems rely on
written rules, search, optimization, or combinations of these with
fitted models. It is therefore safer to say that machine learning powers
many of the AI systems we study, not that every AI system is machine
learning.

Before moving to specific algorithms, we need several basic terms.

\textbf{Features} are the inputs available to the model. \textbf{Labels}
are known outcomes attached to cases in the training data.
\textbf{Training} or \textbf{fitting} is the process of adjusting a
model's internal quantities so that its outputs correspond more closely
to the examples. A \textbf{test set} contains cases that were not used
for fitting and allows us to examine whether the model generalizes.

\subsection{Supervised, unsupervised, and self-supervised
learning}\label{supervised-unsupervised-and-self-supervised-learning}

\textbf{Supervised learning} uses labeled examples. If country-years in
the training data are labeled as war or peace, or parliamentary motions
are labeled by topic, the model learns a mapping from the features to
those known labels. The classifiers in Weeks 2 through 4 are
supervised-learning methods.

\textbf{Unsupervised learning} starts without an outcome label. It looks
for structure in the data, such as clusters of similar cases or
dimensions along which cases vary. Because there is no known correct
label, evaluation is less straightforward. We will discuss the
distinction even though the applied models in the first half of this
course are supervised.

\textbf{Self-supervised learning} is often treated as a branch of
unsupervised learning, although it creates a supervised-style prediction
problem from unlabeled data. The training data do not need labels
supplied by a human, because the data provide the training signal. In
language-model pretraining, parts of the text provide targets for
predicting other parts. Next-token prediction is the main example: the
preceding text is the input and the next token becomes the target.

Large language models are therefore commonly described as being
pretrained through self-supervised learning. They may later undergo
supervised fine-tuning, preference optimization, reinforcement learning,
or other forms of post-training.

Using an LLM to code or label political data is a separate matter. At
that point, we are using an already trained generative model to perform
a classification task. With examples in the prompt, it may act as a
few-shot classifier; without examples, it may act as a zero-shot
classifier. The task is classification, but that does not retroactively
change how the underlying model was pretrained.

\subsection{Generative, reasoning, and agentic
systems}\label{generative-reasoning-and-agentic-systems}

\textbf{Generative models} produce new content rather than only
assigning a predefined label. Large language models generate text by
estimating plausible continuations given the preceding context. Their
ability to produce fluent answers comes from large-scale pretraining and
later post-training, not from looking up a single stored response.

\textbf{Reasoning models} are language models optimized to perform
better on tasks that require multiple inferential steps, often through
additional training and more computation at inference time. Some produce
visible intermediate text before giving an answer. We should not assume
that this text is a literal transcript of an internal reasoning process.
It is model output and must be evaluated as such.

\textbf{Agentic systems} place a model inside a process in which it can
choose actions, use tools, inspect results, and continue working toward
a goal. The model may search, run code, retrieve documents, or call
other services. This expands what can be automated. It also makes
verification harder: if a system searched, selected, summarized, and
coded evidence for us, we must still decide what parts of that process
we can defend as researchers.

\section{Why is this vocabulary
political?}\label{why-is-this-vocabulary-political}

These distinctions are not only technical. They affect regulation,
responsibility, and the distribution of power.

A supervised classifier used to identify potentially fraudulent benefit
claims raises different problems from a generative model drafting
letters to claimants. The systems may differ in their training data,
output, error patterns, and opportunities for appeal. Regulation that
refers only to ``AI'' can miss those differences.

The source of a problem also affects who can address it. Unequal
treatment may arise from the training data, the objective used to fit
the model, post-training decisions, instructions written by the
deploying organization, or the inputs supplied in a particular case.
Responsibility may therefore be distributed across model developers,
vendors, public organizations, and individual users. Saying only that
``the algorithm is biased'' does not tell us which part of the system
produced the result.

The phrase ``the algorithm decided'' creates a related problem. An
organization selected the system, defined the purpose, chose the data
and threshold, and decided how the output would be used. Describing the
final outcome as the algorithm's decision can make those organizational
choices disappear.

\section{An older analogy: artificial political
entities}\label{an-older-analogy-artificial-political-entities}

Political theory and public-administration scholarship give us older
ways of thinking about artificial and collective decision-making. These
were not theories of artificial intelligence in the modern technical
sense. They are useful analogies because they direct our attention to
rules, information, authority, and responsibility.

On the first page of \emph{Leviathan}, Hobbes describes the commonwealth
as an ``Artificiall Man'' (Hobbes 1651). The sovereign is an artificial
person created through political agreement. The famous frontispiece
shows a body composed of many individual people. Hobbes is describing an
artificial political entity, not a machine-learning system. Still, the
image raises a familiar question: how can a constructed entity perceive,
decide, and act in ways that cannot be reduced to one individual inside
it?

Weberian bureaucracy offers a second analogy (Weber 1978). Bureaucracy
is designed to make decisions impersonally through offices, written
rules, files, and established procedures. Its political attraction is
predictability: similar cases should receive similar treatment
regardless of who happens to sit at the desk. In that limited sense, we
can think of bureaucracy as an algorithm implemented through people and
documents. But this remains an analogy. A written administrative rule
and a fitted statistical model are not the same thing. Or are they?

Herbert Simon provides the closest bridge (Simon 1947, 1969). He treated
organizations as information-processing and decision-making systems
while also contributing to the development of artificial intelligence.
Because individuals have limited information, attention, and
computational capacity, organizations use routines and decision
procedures to reach acceptable rather than perfectly optimal outcomes.

These analogies help us ask political questions about contemporary
systems. Who designed the procedure? What information can it use? What
is invisible to it? Who has the authority to override it? And who
answers for the result when it is wrong? The technology is new, but
several of the institutional questions are not.

\chapter{Fitting a function without assuming its
shape}\label{fitting-a-function-without-assuming-its-shape}

We usually want to know how an outcome varies with something else: how
\(Y\) behaves conditional on \(X\), written \(P(Y=y \mid X=x)\).

The most familiar strategy is to assume a shape for that relationship
and then estimate the parameters of the assumed shape. Ordinary least
squares assumes a line. Logit and probit assume particular shapes for
binary outcomes. These are \textbf{parametric} models, and the
assumption is doing a great deal of work.

Assuming a shape buys you real things. You get coefficients you can
interpret substantively, standard errors, a compact summary you can put
in a table, and a direct connection between a theoretical claim and a
quantity you can estimate. Most of what you have done in your other
courses relies on this.

It also costs something. If the true relationship is not the shape you
assumed, the model is wrong in a way that more data will not fix.
Collecting a thousand more observations does not rescue a straight line
drawn through a curve.

When the assumption looks doubtful, there are two responses. The first
is to stay inside the parametric framework and repair the model:
transform a variable, add an interaction, take logarithms. The second is
to use a \textbf{non-parametric} method, which assumes much less about
the shape and lets the data determine it.

\(K\)-nearest neighbors is the simplest non-parametric method there is.
Here is the entire algorithm:

\begin{quote}
To predict the outcome for a case, find the \(k\) cases in your data
most similar to it, and average their outcomes. If the outcome is a
category rather than a number, take the majority vote instead of the
average.
\end{quote}

There is nothing else. No estimation step, no parameters, no fitting in
the usual sense. The model is the data.

\section{What the algorithm actually
did}\label{what-the-algorithm-actually-did}

Take one point on that curve. To produce a prediction for a country with
a per capita GDP of \$2,000, the algorithm found the fifteen countries
in the data closest to \$2,000 on that axis and averaged their infant
mortality. To produce the prediction at \$3,000, it did the same thing
with a neighborhood that had shifted slightly to the right, dropping
some countries and picking up others.

The curve is the trace left behind by that moving neighborhood. It is
not a formula, and it cannot be written as one. It is a record of what
the neighbors did.

This is also why the curve wobbles where the data are sparse. On the
right-hand side there are few countries, so the fifteen nearest
neighbors of a rich country may be spread across a very wide range of
incomes. The algorithm still returns an answer. It does not warn you
that the answer came from a neighborhood stretching across \$40,000.

At \(k=3\) the curve is jagged. It follows every local fluctuation,
including fluctuations produced by the fact that we happen to have these
199 countries rather than some other set. At \(k=150\) the curve is
nearly flat, close to the overall average, and it has erased a
difference between rich and poor countries that is obviously real.

Both failures are informative, and they are opposite failures.

A small \(k\) takes every wiggle in the data seriously. Some of those
wiggles are the relationship we want. Others are noise. A model flexible
enough to reproduce the training data exactly has reproduced the noise
along with the signal, and the noise will not be there next time.

We can state this in one line. Write the outcome as

\[Y = \underbrace{f(X)}_{\text{signal}} + \underbrace{\varepsilon}_{\text{noise}}\]

What we want is \(f\). The term \(\varepsilon\) is whatever is left
over: measurement error, idiosyncrasy, the particular history of the
particular countries in this dataset. It is not a stable feature of the
world, and a model that has learned it has learned something that will
not recur.

So here is the sentence to take away from this week. \textbf{A model
that fits your data perfectly has told you nothing, because all it has
done is recite back the data you already had.} This is the opposite of
the instinct most people arrive with, which is that a closer fit is a
better model.

A large \(k\) fails in the other direction. It averages across countries
that are not comparable, and it produces a model too rigid to represent
a relationship that genuinely exists.

\chapter{Bias and variance}\label{bias-and-variance}

We now have the picture. The vocabulary for it is worth learning,
because it is how everyone else in this literature talks, and because
the two failures it names are genuinely different failures.

Return to the decomposition from earlier:

\[Y = \underbrace{f(X)}_{\text{signal}} + \underbrace{\varepsilon}_{\text{noise}}\]

A model can be wrong about \(f\) in two ways.

\textbf{Bias} is systematic error. The model is too rigid to represent
the shape of \(f\), so it is wrong in the same direction every time, and
it would still be wrong if you handed it a million more countries. The
straight line we drew through the infant mortality data has high bias.
So does \(K\)-nearest neighbors at \(k=150\), which flattens a real
curve into something close to a horizontal line.

\textbf{Variance} is instability. The model is flexible enough to
represent \(f\), but it responds so eagerly to the particular cases in
front of it that a different sample would have produced a noticeably
different answer. It is not systematically wrong. It is just not
reliable, and the specific answer you got is partly an accident of the
data you happen to hold.

The trade-off is that reducing one usually increases the other, which is
what produces the U.

is why it cannot be used to choose anything. The test curve has a
minimum, and finding it is the entire problem.

At \(k=150\) the curves lie almost on top of one another. Run the study
again and you would get essentially the same answer, which sounds like a
virtue until you notice where that answer sits: the box is nowhere near
the red line. The model is stable and consistently wrong. That is bias.

At \(k=40\) the box is both reasonably tight and reasonably close. That
is the whole idea.

Notice what this means for how you read a result. A model with high
variance can be badly wrong without giving any sign of it, because the
fit to the data in front of you looks excellent. Nothing in the output
announces that a different sample would have said something else.

\chapter{Cross-validation}\label{cross-validation}

Now back to the problem we left hanging. We chose \(k\) using one train
and test split, and the choice moved when the seed moved. Two complaints
about the single split, both fair:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  The answer depends on which split we happened to draw, which is
  exactly the instability we just spent a section learning to distrust.
\item
  We set aside thirty percent of the countries and never trained on
  them. With 199 cases that is a real loss of information.
\end{enumerate}

\textbf{Cross-validation} addresses both by rotating the role of the
held-out set.

\section{Leave-one-out}\label{leave-one-out}

Set aside a single observation, train on the remaining \(n-1\), predict
the one you left out, and record the error. Do it again with the next
observation. Repeat \(n\) times and average.

\[\text{RMSE}_{\text{LOO}} = \sqrt{\frac{1}{n}\sum_{i=1}^{n}\left(y_i - \hat{y}_i\right)^2}\]

Every case gets used for training almost every time and for testing
exactly once. Nothing is wasted, and there is no arbitrary split to be
at the mercy of. The cost is that you have to fit the model \(n\) times.

\section{k-fold}\label{k-fold}

The practical compromise is to hold out a group instead of a single
case. Split the data at random into a number of roughly equal folds.
Hold out the first fold, train on the rest, and record the error on the
fold you held out. Then hold out the second fold, and so on, until every
fold has served once as the test set. Average the results.

\pandocbounded{\includegraphics[keepaspectratio]{handouts/w02-knn_files/figure-pdf/unnamed-chunk-11-1.pdf}}

\[\text{CV RMSE} = \sqrt{\frac{1}{\text{nfold}}\sum_{f=1}^{\text{nfold}} \text{MSE}_f}\]

\textbf{One warning about names before the code.} The \(k\) in
``\(k\)-fold'' has nothing whatever to do with the \(k\) in
``\(K\)-nearest neighbors.'' They are two unrelated numbers that
unfortunately share a letter, and we are about to choose one of them
using the other. To keep them apart, the code below calls the number of
folds \texttt{nfold} and never \texttt{k}.

necessarily identical, since \texttt{caret} draws its own folds. If the
two disagree by more than a few units of \(k\) on a curve this flat,
that is the flatness talking rather than a real disagreement.

\chapter{More than one feature, and the problem of
units}\label{more-than-one-feature-and-the-problem-of-units}

So far similarity has meant closeness on a single axis, which is easy.
With several features we need a general definition of distance, and the
usual one is Euclidean distance. For a case \(f\) with features
\((x_{f1}, \dots, x_{fp})\) and a case \(i\) in the training data,

\[d_{if} = \sqrt{\sum_{j=1}^{p}\left(x_{fj} - x_{ij}\right)^2}.\]

This is the straight-line distance you already know, extended to more
than two dimensions. And it introduces a problem that is easy to miss
and consequential when you do.

Our features are measured on very different scales. Per capita GDP runs
from well under one up to about a hundred, in thousands of dollars.
Percent urban runs from zero to a hundred. Fertility runs from about one
to about seven, and female life expectancy from the high forties to the
high eighties.

The filled red point is the country we are predicting for. The circled

almost exactly the target's income and are spread across nearly the
whole range of fertility, from around one child per woman to well above
the average. Per capita GDP spans about a hundred units on this scale
and fertility spans about six, so a difference of a few units of income
outweighs the entire fertility axis. The algorithm did not ignore
fertility because anybody judged it unimportant. It ignored it because
of the units it happens to be measured in.

Note also what the model would have reported. Both versions return
predictions. Neither prints a warning. The left-hand model would have
gone into a paper as a two-feature model, and the fact that it was a
one-feature model in disguise would appear nowhere in the output.

Stay with that, because it is not a technical footnote. The algorithm's
entire operation rests on its definition of ``similar,'' and that
definition was just set by two choices: which features we included, and
how we scaled them. Neither choice required anyone to make a claim about
the world. Had we left the units alone, the model would have decided
that countries are similar when their incomes are similar, and it would
have reported that decision as a finding rather than as an artifact of
the fact that GDP happens to be counted in dollars.

\chapter{What this model cannot tell
you}\label{what-this-model-cannot-tell-you}

The model has no coefficients. There is no number to report saying how
much per capita GDP matters, no standard error, no statement of the form
``a one-unit increase in \(X\) is associated with a change in \(Y\).''
The model cannot be written down apart from the data it holds.

More importantly, it has said nothing about \emph{why} infant mortality
is lower in richer countries. It has found that countries with similar
incomes tend to have similar infant mortality, and it can use that to
predict. That is a prediction, in exactly the sense we distinguished
last week, and it does not become an explanation by performing well.

There is a second limit, and the neighborhood figures above showed it. A
model of this kind answers every question put to it, at the same
apparent level of confidence, whether the case sits in a crowded part of
the data or alone at the edge of it. The richest country in this dataset
gets a prediction assembled from neighbors spread across tens of
thousands of dollars of income. That prediction is printed in the same
format, to the same number of decimal places, as one built from
twenty-five genuinely similar cases. Nothing in the output distinguishes
them.

\chapter{The politics of similarity}\label{the-politics-of-similarity}

The rule at the center of this week is that cases similar to past cases
receive what those past cases received.

That is also a fair description of precedent in law, of case-based
reasoning in administration, and of the Weberian bureaucratic ideal we
discussed last week, in which similar cases are treated alike regardless
of who happens to be at the desk. Consistency of this kind is not a
defect. It is one of the oldest arguments for rule-bound government, and
part of what makes an administration predictable enough to be held to
account.

What changes when the rule is a fitted model is who defines similarity,
and how visibly. In \(K\)-nearest neighbors that definition came from
feature selection and rescaling, decisions made early, made quietly, and
almost never revisited or documented once the system is running. Nobody
writes them down as a policy, because they do not look like a policy.

And a model of this kind can only reproduce the pattern in the cases it
was given. If the treatment recorded in those cases was unjust, then
similarity to past cases carries the injustice forward, and it does so
with the appearance of perfect consistency. The system is not
malfunctioning when this happens. It is doing precisely what it was
built to do.

\chapter{Trees and Random Forests}\label{trees-and-random-forests}

\emph{Week 3, 16 September}

Last week's method concealed nothing, in the sense that every prediction
\(K\)-nearest neighbors produced could be traced back to a small set of
countries that could be located on a scatterplot. This week begins from
the same premise, with a model that can be drawn on a whiteboard and
read aloud as a sequence of rules, and then abandons that transparency
deliberately, in exchange for a considerably better model.

The session therefore stages a tension that runs through much of
contemporary machine learning. On the one hand, a model whose reasoning
can be inspected is easier to defend, to audit, and to explain to
somebody who has to act on its output. On the other hand, the models
that predict best are frequently the ones whose reasoning cannot be
inspected at all. Trees and forests are unusually well suited to
examining this tension, because the movement from the first situation to
the second occurs within a single family of methods and can be observed
at each step.

\section{What trees are good at, and what they are
not}\label{what-trees-are-good-at-and-what-they-are-not}

Tree models in statistical learning bear an obvious kinship to decision
trees as we ordinarily understand them, and they have been used widely
for prediction. It is worth setting out at the start what they offer and
what they cost.

\textbf{Benefits.}

\begin{itemize}
\tightlist
\item
  They capture interactions between features and non-linear associations
  without being instructed to look for them.
\item
  They handle categorical variables well, and the results remain
  interpretable.
\item
  They are relatively fast compared with most other machine-learning
  algorithms.
\item
  \textbf{They do not require the features to be rescaled.}
\end{itemize}

The final point deserves a moment, since it undoes an entire section of
last week. \(K\)-nearest neighbors was at the mercy of the units in
which its features happened to be measured, and we devoted considerable
effort to placing everything on a common scale so that income would not
swamp fertility. A tree, however, never compares two features to each
other. Instead, it asks one question at a time, about a single variable,
and on that variable's own scale, so that multiplying a feature by a
thousand changes nothing whatever and the problem simply does not arise.

\textbf{The disadvantage,} and it is a serious one, is that a single
tree does not predict well out of sample.

That tension is the shape of the week, in that everything after the
first third is an attempt to retain the benefits while addressing the
disadvantage, by growing a forest of trees and allowing them to vote.

Both are step functions constructed from local averages, and neither was
told the shape of the relationship in advance. The difference between
them lies entirely in the manner in which the neighborhoods are
determined.

\(K\)-nearest neighbors uses a window of fixed size that slides along
the axis. Every prediction averages exactly ten countries, whether those
ten lie within a few hundred dollars of one another or are distributed
across forty thousand. This is why the curve becomes unstable on the
right, where the data thin out: the window preserves its count while
losing its substantive meaning.

The tree, by contrast, uses regions of fixed content, having selected
where to cut and therefore how wide each region should be, narrowly
where the outcome changes quickly and broadly where it does not. The
cost of proceeding this way is that the steps are coarse. The gain,
however, is that the width of a neighborhood becomes a decision the
algorithm reached about the data, rather than a number imposed upon it
in advance.

\subsection{What the algorithm is
minimizing}\label{what-the-algorithm-is-minimizing}

We are splitting the feature space \(X = \{x_1, x_2, \dots, x_k\}\) into
smaller rectangles, or boxes. If we can identify a pattern of splits
with low prediction error on the training data, we can then predict for
a new case by determining which box it belongs to.

Roughly, a tree may be thought of as a \(K\)-nearest neighbors algorithm
in which \(k\) is dynamic: the neighborhood is a box rather than a
window, and the boxes are wide where the data are sparse and narrow
where they are dense, rather than fixed in advance. The figure above is
that proposition drawn, and it is worth returning to whenever the
relationship between the two methods becomes unclear.

Formally, for a continuous outcome:

\begin{align}
\min_{R_1, R_2, \dots, R_J} \sum_{j=1}^{J} \sum_{i \in R_j} (y_i - \hat{y}_{R_j})^2
\end{align}

The boxes \(R_j\) are chosen so as to minimize the total squared
deviation of observations from the mean response within each box. In
principle there are infinitely many ways of defining the boxes, and
evaluating all of them is computationally impossible. A
\textbf{recursive partitioning} procedure is therefore used instead:

\begin{itemize}
\tightlist
\item
  Scan every feature to identify the one whose split yields the best
  improvement, and split there.
\item
  Repeat within each resulting box, and continue until splitting becomes
  too costly or a pre-set size is reached.
\end{itemize}

This is a \textbf{greedy} approach, in that at each step it takes the
split that appears best at that moment, without considering the
consequences for the splits beneath it. The resulting tree is therefore
a good tree arrived at through a sequence of locally sensible decisions.
It is not the best one, and the best one is not known.

\subsection{Cost complexity, and the parameter that plays the role of
k}\label{cost-complexity-and-the-parameter-that-plays-the-role-of-k}

Left to itself, the procedure continues splitting until every leaf is
small and homogeneous, which fits the training data very well indeed.
Last week, however, taught us to regard that result with suspicion
rather than satisfaction.

The standard remedy rewrites the problem as

\begin{align}
C(T, y) = L(T, y) + \alpha |T|
\end{align}

where \(L(T, y)\) is the loss from fitting outcome \(y\) with tree
\(T\), and \(|T|\) is the number of nodes. Small loss is always
preferred. Nevertheless, we do not want a tree so complex that it
captures every fluctuation in the training data and consequently
predicts poorly outside it, and the size of the tree is therefore
penalized, with \(\alpha\) determining how heavily that penalty is
applied.

A large \(\alpha\) makes complexity expensive and returns a small tree,
which may in consequence fit poorly, whereas a small \(\alpha\) permits
the tree to grow large. \textbf{Here} \(\alpha\) is analogous to \(k\)
in \(K\)-nearest neighbors, and, as with \(k\), no value is correct in
advance.

The question of how to choose it has the same answer as last week, and
as most weeks: cross-validation.

Three samples drawn from the same data yield three trees, and the

split changes, everything beneath it changes with it, since every
subsequent question is asked only of the cases that the first question
directed that way.

The vocabulary for this was established last week, and the term is
\textbf{variance}, in the sense that the model responds to the
particular cases placed before it rather than to the structure
underlying them. A single tree has low bias, since given sufficient
depth it can represent almost any shape, and high variance, since which
shape it represents depends heavily on the sample. The greedy procedure
aggravates the problem, because a single early decision taken on a
narrow margin propagates through everything below it.

A single tree is thus readable and unreliable at the same time, and the
response, perhaps counterintuitively, is to stop reading it.

\subsection{From bagging to random
forests}\label{from-bagging-to-random-forests}

\textbf{Bagging}, an abbreviation of bootstrap aggregating, is the first
idea. The data are resampled with replacement a sufficient number of
times that trees with good explanatory power are captured, a tree is
fitted to each sample, and their predictions are averaged. The procedure
is computationally intensive, and it works for the reason averaging
generally works: individually noisy estimates, once averaged, are less
noisy, provided their errors are not all the same error.

That proviso, as it happens, is precisely where the method acquires its
name. \textbf{Random forests begin from bagging and add a second
randomization.} Rather than scanning all the features at each split, the
algorithm samples a subset of \(m\) variables and must then select its
split from among those alone.

The rationale is precise. If income is the strongest predictor, for
instance, then every bagged tree splits on income first, and the trees
therefore resemble one another closely and err in the same places.
Requiring most trees to proceed without it at any given split breaks
that correlation. The individual trees thereby become \textbf{worse},
and yet their average becomes \textbf{better}.

This is the proposition to carry out of the week. A forest is not an
attempt to build one excellent model. It is an attempt to build many
mediocre models whose errors point in different directions, and then to
let them vote.

Two parameters govern the procedure: \(B\) is the number of bootstrapped
trees, and \(m\) is the number of variables sampled at each split. A
common choice is \(m = \sqrt{p}\), where \(p\) is the number of
features. Notably, when \(m = p\) the random forest reduces to bagging.

accuracy on a two per cent outcome is maximized by predicting zero
indefinitely, so that the model did precisely as it was instructed.

This is the stump from the beginning of Part II, returning in a more
elaborate form. The single tree refused to split because no split
improved accuracy; the forest grew nine hundred trees and then predicted
almost nothing, for the same reason. We repaired the tree by telling it
that the rare class mattered, and we declined to repair the forest, and
the two figures should be read together. The disease is identical in
both cases, and it lies in the objective rather than in the algorithm.
\textbf{\texttt{caret} tuned \texttt{mtry} so as to maximize accuracy,
which is to say that it tuned toward the useless model, and reported
success in doing so.}

Nothing in the output announced this. The accuracy appeared excellent,
the cross-validation was correctly specified, and the test set was
genuinely held out. Every methodological requirement was satisfied, and
the result is a model that has not once predicted the outcome it was
built to predict.

This is the argument of the second reading for this week (Muchlinski et
al. 2016), and it is the reason that article exists. Week 6 takes up the
repair in full, covering precision, recall, the F1 score, thresholds,
and class weighting, together with the question of what to do when one
error costs substantially more than the other. For the present, the
diagnosis matters more than the cure.

\subsubsection{The four cells}\label{the-four-cells}

The table printed above is a \textbf{confusion matrix}, and naming its
cells requires first determining which class counts as
\textbf{positive}, which is a decision made by the analyst rather than a
property of the data. Here the positive class is war onset.

A \textbf{false positive} is a country flagged as heading toward civil
war that does not in fact experience one, whereas a \textbf{false
negative} is a civil war that nobody anticipated. These are not the same
error, and no serious application treats them as equivalent. Which of
them one would rather commit is a political and ethical judgment about
consequences, and accuracy collapses the two into a single number
precisely by declining to pose the question.

\subsection{Variable importance, and what it does not
mean}\label{variable-importance-and-what-it-does-not-mean}

We surrendered the readable tree, and variable importance is what is
returned to us in its place.

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{varImpPlot}\NormalTok{(rf}\SpecialCharTok{$}\NormalTok{finalModel, }\AttributeTok{main =} \StringTok{"Variable importance"}\NormalTok{)}
\end{Highlighting}
\end{Shaded}

\pandocbounded{\includegraphics[keepaspectratio]{handouts/w03-trees-forests_files/figure-pdf/unnamed-chunk-23-1.pdf}}

The underlying idea is straightforward. For each feature, one measures
the extent to which the forest's performance depends upon it, either by
totalling the improvement that feature produced across all the splits in
which it was used, or by permuting its values and observing how far the
predictions deteriorate. Thus a feature that can be scrambled without
consequence was evidently not contributing much.

Since the forest is bootstrapped, features that genuinely matter will on
average be selected and used more frequently than others, and this is
what makes the ranking meaningful at all.

The limits of the measure, however, matter more than the figure itself.

\textbf{Importance is not effect size.} The plot has no interpretable
units. A feature twice as high as another is not twice as influential in
any substantive sense, and the numbers are not comparable across models
or datasets.

\textbf{Importance carries no sign.} Nothing here indicates whether
higher income raises or lowers the risk of onset. A feature may sit at
the top of the plot with a relationship that is positive, negative, or
U-shaped, and the ranking cannot distinguish among them.

\textbf{Correlated features divide their importance between them.} Where
two features carry substantially the same information, the forest uses
them interchangeably, and each appears half as important as either would
appear alone. A feature may therefore look unimportant because it has a
twin rather than because it is irrelevant. In these data, where income,
population, and several regime measures are entangled with one another,
the possibility is not hypothetical.

\textbf{Impurity-based importance is biased} toward features with many
distinct values, so that continuous variables tend to outrank binary
ones for reasons unrelated to the world. It is worth comparing where
\texttt{Oil} and \texttt{nwstate}, which are binary, sit relative to
\texttt{gdpenl}, which is not.

\textbf{None of it, finally, is causal.} Importance describes what the
model used in order to predict. It says nothing about what would follow
from changing a feature, since nothing in the procedure ever posed that
question.

The last point has a practical edge, in that variable importance is
regularly presented, in policy briefs and in press coverage, as
identifying the drivers of a problem. What it identifies is the set of
predictors that a particular fitted model found useful on a particular
dataset. These are different claims, and the distance between them is
where a good deal of poor AI-informed policy analysis is located.

\section{Prediction, forecasting, and early
warning}\label{prediction-forecasting-and-early-warning}

Week 1 distinguished prediction from forecasting: prediction estimates
an outcome for a case the model has not seen, whereas forecasting
estimates one that has not yet occurred. Everything above is prediction,
since our test set consists of country-years drawn at random from the
same period as the training set.

The third reading for this week concerns the other activity ({Hegre et
al.} 2019). ViEWS is an operating early-warning system that publishes
monthly forecasts of political violence for months that have not yet
occurred, and the difference is not merely presentational.

As soon as the target is the future, a random split becomes
indefensible. If the model trains on 1995 and 1999 and is tested on
1997, it has observed the years on either side of the case it is
predicting, and it will make use of them. Forecasting therefore requires
splitting on time: training up to a date, forecasting beyond it, and
accepting that one cannot look ahead. Nearly every published forecasting
model that appeared too good to be true was too good on account of some
version of this.

A subtler problem remains, which cross-validation does not address, in
that cross-validation assumes cases to be interchangeable while
country-years plainly are not. Sudan in 1996 is not independent of Sudan
in 1995, and a fold that holds one while the other trains the model is
leaking information. This is the structural difference flagged at the
start of Part II, and it has a name: the observations are not
independent, while the standard resampling procedures assume that they
are. Week 6 returns to the problem and to the ways in which it can be
mitigated.

\section{The politics of early
warning}\label{the-politics-of-early-warning}

A forecast is not merely an analysis that happens to concern the future.
It is, rather, an object produced in order to be acted upon, and that
purpose changes what its errors mean.

Suppose a system of this kind flags a country as being at elevated risk.
Consequences follow, in investment decisions, aid allocations, insurance
premiums, travel advisories, diplomatic posture, and on occasion in the
argument for intervention. The forecast thereby enters the politics of
the country it describes.

That observation should be combined with the base rate. Thus, where the
outcome occurs in two per cent of cases, even a model with genuinely
good discrimination will produce considerably more false alarms than
true warnings, simply because there are so many more non-events
available to be wrong about. A country may therefore be flagged, bear
the consequences of having been flagged, and have been a false positive
throughout. It will not be informed of this, and the system has no means
of establishing it either, until the year passes without incident and
the case leaves the window.

Moreover, a forecast can act upon the world it describes. If a warning
of instability withdraws investment, and withdrawn investment raises the
likelihood of instability, then the model has participated in the
outcome it predicted and will appear more accurate for having done so.
This is not a defect in the statistics. It is, instead, what occurs
whenever a prediction about people is published to people who have the
power to respond to it.

The closing question last week concerned who defines similarity, and the
closing question this week concerns who defines the threshold. Somewhere
between the forest's vote share and a red mark on a map, a number is
selected that determines which countries are flagged, and that number
sets the ratio of false alarms to missed wars. It is among the most
consequential decisions in the entire pipeline, it is rarely made by
anybody who bears its consequences, and it almost never appears in the
write-up.

\section{Reading}\label{reading-2}

Fearon, J. D., and Laitin, D. D. 2003. ``Ethnicity, Insurgency, and
Civil War.'' \emph{American Political Science Review} 97(1): 75--90.
(Fearon and Laitin 2003)

These are the data used above and the specification fitted above. The
article should be read for its argument about the causes of civil war,
and it is worth noting throughout that it is an explanatory article. Its
authors are not attempting to predict onset; they are attempting to
explain it, and the difference between those two objectives is the
thread running through this week.

Muchlinski, D., Siroky, D., He, J., and Kocher, M. 2016. ``Comparing
Random Forest with Logistic Regression for Predicting Class-Imbalanced
Civil War Onset Data.'' \emph{Political Analysis} 24(1): 87--103.
(Muchlinski et al. 2016)

This one should be read for its argument about rare outcomes rather than
for its implementation, and, if time permits, alongside the critical
exchange it provoked, since the disagreement is instructive about what a
performance comparison can and cannot settle.

Hegre, H., et al.~2019. ``ViEWS: A Political Violence Early-Warning
System.'' \emph{Journal of Peace Research} 56(2): 155--174. ({Hegre et
al.} 2019)

This should be read as a description of a system that is actually in
use, rather than as a methods article. Particular attention is worth
giving to what its authors say about how the forecasts are intended to
be interpreted, and by whom.

\textbf{Recommended, not required.}

Pinckney, J., and RezaeeDaryakenari, B. 2022. ``When the Levee Breaks: A
Forecasting Model of Violent and Nonviolent Dissent.''
\emph{International Interactions} 48(5): 997--1026. (Pinckney and
RezaeeDaryakenari 2022)

This article forecasts both armed and unarmed conflict at the
country-year level, and it does so by training eight machine-learning
algorithms and combining them into five forecasting ensembles. The
relevance to this week is direct, in that the logic of the random forest
reappears one level higher: where a forest averages many trees whose
errors point in different directions, an ensemble forecast averages many
algorithms on the same reasoning. It is also worth reading for the
contrast with the cases above, since the outcome of interest includes
nonviolent mobilization rather than civil war alone, and unarmed
uprisings are neither as rare nor as well measured.

\section{Questions for the session}\label{questions-for-the-session-2}

Come with a view on at least two of these.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  Fearon and Laitin set out to explain civil war, whereas we used their
  variables to predict it. What did we learn that they did not, and what
  did they establish that our model cannot?
\item
  A single tree is readable and unreliable, while a forest is reliable
  and unreadable. For a political scientist, which of these failures is
  the more serious, and does the answer depend on the purpose the model
  is to serve?
\item
  The forest deliberately makes each tree worse, by withholding features
  from it, in order that the ensemble should be better. Is there
  anything analogous in the way political institutions aggregate
  judgments? Committees, juries, federal structures, and multiple veto
  players are all admissible.
\item
  Our model achieved very high accuracy and predicted almost no wars,
  and every technical step was performed correctly. What does this
  suggest about the relationship between methodological correctness and
  usefulness?
\item
  Variable importance is regularly reported in policy documents as
  identifying the drivers of a problem. Write the one sentence you would
  add to such a document in order to make it honest, and state what
  would be lost in the process.
\item
  Who should select the threshold at which a forecast becomes a warning,
  and to whom should that selection be explained? Note that those
  bearing the cost of a false alarm and those bearing the cost of a
  missed war are generally not the same people.
\end{enumerate}
